# 08-Memory Start：开发前理解

> 这一页先讲清楚第八章为什么存在、目标是什么。不要先读记忆提取和文件回退实现，开发到对应阶段再读。

## 背景：第七章解决了什么，还缺什么

第七章解决了一个“进程还活着时”的问题。

用户让 Agent 做一个很长的任务，历史会越来越大。第七章会把大工具输出落盘、把旧历史压缩成摘要，因此同一轮终端会话可以继续运行。

但关闭终端后，仍然会发生：

```text
昨天：
  你：修复登录，但不要改 API。
  Agent：已经读完 auth 代码，正在改前端校验。

今天重新启动：
  Agent：不知道昨天做了什么，也不知道“不要改 API”。
```

第七章已经把一部分会话写成 JSONL，尤其是压缩边界；但它还不能列出旧会话、不能恢复到指定会话，也不会保存每一轮完整对话。

第八章就是补上“跨进程记忆”。目标不是让 Agent 记住所有废话，而是让它在下次工作时知道三件真正有用的事：

```text
这个项目有什么固定规则？
上一次任务进行到哪里？
这个用户有哪些长期偏好？
```

## 本章目标

完成后，QiCode 应该从“每次启动都失忆”变成下面这样：

```text
启动新会话
  -> 自动读到项目规则：例如 pnpm、禁止改 API、提交前 typecheck
  -> 自动看到少量长期记忆摘要：例如用户偏好中文回复

正常对话
  -> 用户消息和 Agent 最终回复持续写入 JSONL
  -> 退出或崩溃后，历史仍在磁盘

下次启动
  -> /resume 列出会话
  -> /resume <id> 恢复到上次工作现场
  -> 新消息继续追加到同一个 session 文件
```

另外，Agent 会在一轮任务自然结束后，后台判断有没有值得长期保存的信息。例如用户说“以后测试不要每步都跑”，才保存成笔记；普通的一次性聊天不会都变成记忆。

## 三层记忆分别解决什么

### 1. 项目指令：项目明确要求的规则

来源是用户手写的 Markdown 文件，例如：

```text
本项目使用 pnpm。
不要修改数据库 schema。
提交前必须跑 typecheck。
```

它在启动时加载，在第一轮模型请求前注入。它的特点是：**人明确写的，优先级高，不能靠模型猜。**

### 2. 会话存档：上次工作做到哪里

来源是每轮用户和 Agent 的对话，保存在：

```text
.qicode/sessions/<sessionId>.jsonl
```

它解决的是“昨天没做完，今天从哪里继续”。第七章的 `compact_boundary` 也在这里，它告诉恢复逻辑：很早的历史已经被摘要替代，不能重新全部塞回上下文。

### 3. 长期记忆：跨多个任务仍有用的偏好和知识

来源是 Agent 在对话结束后后台提取的少量信息，例如：

```text
用户偏好：回复使用简体中文。
纠正反馈：这个仓库不要频繁跑完整测试。
项目知识：认证模块不允许改变对外 API。
参考资料：某个内部文档的用途。
```

它不是完整聊天记录。启动时只注入“笔记标题和描述”的索引；模型需要正文时再读对应 Markdown 文件。

## 一条总链

```text
启动
  -> 加载项目指令
  -> 加载长期记忆索引
  -> 作为第一条系统提醒注入 Conversation

正常对话
  -> user / assistant 消息追加 JSONL
  -> 自动压缩时追加 compact_boundary
  -> Agent 自然结束后后台提取长期记忆

恢复
  -> /resume <id>
  -> 读取 JSONL 最后一个 compact_boundary
  -> 重建摘要 + 保留消息 + 边界后的新消息
  -> 后续继续写同一份 JSONL
```

## 本章不做什么

- 不使用向量数据库。
- 不自动恢复最近会话，必须用户显式 `/resume`。
- 不做云同步、团队共享或跨机器记忆。
- 不把所有聊天内容都自动存成长期笔记。
- 不做运行期间热加载项目指令。

## 开发前你只要记住

第八章的核心不是“记得越多越好”，而是正确分层：

```text
项目规则：人写的，启动就要遵守。
会话记录：用于继续未完成工作。
长期笔记：只保留跨任务仍然有价值的信息。
```

第一阶段会先补全 session 的“统一 ID、会话列表、清理”能力，让第七章已经写下的 JSONL 真正能被用户管理和恢复。

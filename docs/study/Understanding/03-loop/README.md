# 03-Loop 开发前认识与理解

> 本文用于开发前学习。以当前源码为准：`src/agent/agent.ts` 目前仍是“最多一批工具 + 第二次生成最终回答”的单轮闭环；本章规划要把它扩展为真正的多轮 Agent Loop。

## 一、为什么 Loop 要单独拆成一章

第 02 章已经解决了“模型可以请求工具，并由 QiCode 在本机执行”的问题，但流程只推进一次：

```text
模型请求工具 -> QiCode 执行 -> 结果回灌 -> 模型回答
```

如果模型在第二次回答中又发现需要另一个工具，当前代码会拒绝第二批调用。复杂任务就只能停下来让用户再次输入。

第 03 章单独拆分，是因为它改变的不是某一个工具，而是整个任务的控制方式：Agent 要能够重复执行“请求模型、执行工具、回传结果”，直到模型给出最终文本或触发安全停止条件。它会同时影响 Agent、Provider 事件、工具调度、Conversation、取消信号和 TUI 状态，所以必须先建立整体认识，再分小步开发。

## 二、本章要完成什么

本章目标不是增加更多工具，而是让已有工具能够被连续编排：

1. 把第 02 章单轮闭环改为 ReAct 多轮循环。
2. 每轮都把 assistant 的工具调用和工具结果按顺序写入历史。
3. 用统一事件通知 TUI：文本、工具开始/结束、用量、轮次、错误和结束原因。
4. 连续只读工具可以并发，写入和命令工具保持串行。
5. 支持最大轮次、未知工具、流错误和用户取消等停止条件。
6. 统计跨轮 token，并展示当前迭代轮次。
7. 为 Plan Mode 预留只读工具和计划提醒的两段式流程。

本章仍然不做上下文压缩、权限确认、沙箱、持久化、子 Agent 和完整计划文件工作流。

## 三、用户实际经历的流程

以“读取 A 文件，根据内容新建 B 文件”为例：

```text
用户输入
  |
  v
App.submit()
  |
  v
Conversation 保存用户问题
  |
  v
Agent.run() 开始第 1 轮
  |
  v
Provider.stream() 询问模型
  |
  v
模型请求 ReadFile(A)
  |
  v
Agent 发出 tool_use 事件
  |
  v
StreamingExecutor -> ToolRegistry -> ReadFile
  |
  v
工具结果写入 Conversation
  |
  v
Agent 开始第 2 轮，再次询问模型
  |
  v
模型根据 A 的内容请求 WriteFile(B)
  |
  v
执行写入，结果再次回灌
  |
  v
Agent 开始下一轮
  |
  v
模型不再请求工具，输出最终文本
  |
  v
TUI 显示完成，回到空闲状态
```

这里最重要的变化是：**循环由 Agent 控制，TUI 不负责判断下一步是否继续。**

## 四、当前代码与本章目标的边界

当前可以在 `src/agent/agent.ts` 看到：

- `run()` 先请求一次模型；
- 有工具调用就执行一批工具；
- 工具结果回灌后只允许第二次模型请求；
- 第二次再次请求工具时，返回错误，不执行第二批。

因此，下面这条流程是当前代码已有的：

```text
第一次模型请求 -> 一批工具 -> 工具结果 -> 第二次模型请求 -> 结束
```

而本章开发后要变成：

```text
while (模型仍请求工具) {
  请求模型 -> 执行工具 -> 结果回灌
}
```

## 五、架构地图

```text
TUI App
  |
  v
Agent.run()  —— 只负责控制循环和停止条件
  |      |       |        |
  |      |       |        +--> Conversation：保存每轮消息
  |      |       +-----------> StreamingExecutor：执行工具批
  |      +-------------------> ToolRegistry：按名字找到工具
  +--------------------------> Provider：请求模型并产出统一事件
                                  |
                                  +--> Anthropic / OpenAI / 兼容端点
```

### 模块四问

| 模块 | 负责什么 | 谁调用它 | 它调用谁 | 为什么需要它 |
| --- | --- | --- | --- | --- |
| `Agent` | 控制多轮请求、工具执行、结果回灌和停止 | `App.submit()` | `Provider`、`StreamingExecutor`、`Conversation` | 把复杂编排从 TUI 中抽离，能独立测试 |
| `Provider` | 和模型 API 通信，把厂商流转换为统一事件 | `Agent` | HTTP、SSE、Anthropic/OpenAI 适配器 | 上层不需要知道不同协议的 JSON |
| `StreamingExecutor` | 执行已经收集完整的工具调用 | `Agent` | `ToolRegistry`、具体 Tool | 把“问模型”和“操作本机”分开 |
| `ToolRegistry` | 注册工具、按名称查找、提供工具定义 | `App`、`Agent`、Executor | `Tool` 接口 | 避免 Agent 写大量 `if/else` |
| `Conversation` | 保存用户、助手、工具调用和工具结果 | `App`、`Agent`、`Provider` | 消息数组和克隆逻辑 | 下一轮模型必须携带完整因果链 |
| `TUI` | 消费 AgentEvent 并展示状态 | `main.tsx` / Ink | `Agent`、ChatView、ToolDisplay | 展示层不应该理解 Loop 内部细节 |

## 六、建议先掌握的 10 个问题

回答时先说关键字，再用自己的话展开。

1. **第 02 章的单轮闭环和第 03 章的 Loop 有什么区别？**
   - 关键字：一次工具批次 vs 任意多轮；第二次工具被拒绝 vs 继续执行；安全停止。
2. **为什么循环应该放在 Agent，而不是 App/TUI？**
   - 关键字：业务编排与界面解耦；可测试；TUI 只消费事件。
3. **Agent 每一轮需要保存哪些状态？**
   - 关键字：iteration、累计文本、thinking、toolUses、stopReason、未知工具次数、取消状态。
4. **模型什么时候算完成？**
   - 关键字：本轮没有工具调用，纯文本就是最终回答。
5. **为什么必须设置最大迭代次数？**
   - 关键字：模型幻觉、工具失败重试、成本和死循环保护。
6. **Provider 为什么不能直接返回最终文本？**
   - 关键字：Provider 只负责协议适配；Agent 需要知道工具调用、结果和下一轮。
7. **为什么工具结果必须再次写入 Conversation？**
   - 关键字：模型没有本机记忆；下一轮需要 assistant tool_use 与 tool_result 配对。
8. **为什么连续只读工具可以并发，写入和命令要串行？**
   - 关键字：只读通常无副作用；写入/命令可能互相影响；保持模型给出的顺序。
9. **取消一轮对话时，为什么不能简单退出进程？**
   - 关键字：Esc/Ctrl+C 只取消当前请求；空闲时 Ctrl+C 才退出；历史仍要合法。
10. **为什么 Agent 对外要使用事件，而不是直接操作 TUI？**
    - 关键字：单向数据流、解耦、可测试、未来可替换终端界面。

## 七、推荐学习顺序

1. 先阅读本文和 `docs/plan/03-loop/spec.md` 的目标、边界、验收标准。
2. 再看 `src/agent/agent.ts`，只读 `run()` 的当前单轮流程，不要一开始读全部 Provider。
3. 画出“当前流程”和“目标 Loop 流程”两张图。
4. 用四问复述 `Agent`、`Provider`、`StreamingExecutor`、`Conversation`。
5. 开发时按 `task.md` 的小阶段推进，每完成一阶段再做一次真实终端测试。
6. 代码完成后再更新 Debug 文档中的真实行号和断点。

## 通过标准

你能用自己的话讲清：模型如何决定继续、谁执行工具、结果如何进入下一轮、哪些条件会让循环停止，以及为什么这些判断不能放在 TUI 里。

# 第二期需求：让 QiCode 真正完成编码任务

日期：2026-11-06。状态：新版规划，未实现。代码基线：`2021d9d` / v0.1.6。

## 1. 本期要改变什么

用户说“修复这个问题”“帮我加这个功能”后，QiCode 应自主完成：定位相关代码 → 修改 → 运行合适的验证 → 根据失败结果修复 → 给出可检查的交付。只有真实阻塞、授权边界或执行预算耗尽时才停止并说明原因。

例：“修复配置加载对空字符串处理错误，并加回归验证”。交付应当是工作区真实 diff、能覆盖该问题的验证及执行结果；不能只解释改法，不能改完即宣称完成，也不能每一步都要求用户输入“继续”。

保持简洁：一条主 Agent 执行链、现有六个基础工具、必要的进度与授权。Team、通用工作流引擎、更多 MCP 和终端装饰均不是本期成功条件。

## 4. 需求与优先级

### P2-R01 可重复的真实任务基准（P0，最先做）

- 固定 10 个本地仓库任务和外部验收器，保存初始快照、用户输入、成功条件与允许范围。
- 包含 bug 修复、功能增量、多文件修改、配置调整和真实失败后修复，不能只用“读取 README”充当编码能力。
- 在指定模型上记录原版 QiCode、新版 QiCode 的完整运行证据；用 pi 做条件可比的参考，模型、端点、任务输入、预算与权限配置必须记录。
- 一次运行从干净临时副本开始。记录时间、token、工具、错误、授权次数和用户追加指令次数；自动验收器运行在 Agent 结束后，Agent 不能改验收器。
- 模型调用质量与运行时分别评分：工具协议探测失败时明确模型/端点不满足本轮条件，不用扩大循环次数掩盖。

### P2-R02 工具调用和停止原因可信（P0）

- 保留原始停止原因并规范化为正常结束、工具调用、长度截断、中断、协议错误等类别；正常结束必须有协议终止证据。
- 断流、参数 JSON 损坏、参数缺失/错类型、截断中看似可解析的写入参数，不得作为正常工具执行。
- 每次执行前按 schema 校验；错误以明确工具结果反馈给模型。统一入口对内置工具和 MCP 生效，不让各工具静默兜底掩盖协议问题。
- 对可恢复协议失败允许最多 2 次重试/重新生成；不重复已执行工具。未解决则以失败结束并保存现场。
- 两种现有协议保持不变，不增加第三协议或替换整个 Provider 层。

验收：损坏 JSON、错类型、length/max_tokens、SSE 无终止断流四类场景均不产生不完整写入；每个已提交调用有配对结果或明确未执行记录，下一次请求保持协议合法。

### P2-R03 从建议型回答转为任务执行（P0）

- 行为指令明确区分问答、仅规划和执行请求；执行请求默认先读取相关代码并落地修改，相关验证通过或确有阻塞才交付。
- 尊重已有 Plan、用户禁止写入等约束；简单问答直接回答，不强迫每条消息跑工具或生成计划。
- 多步骤任务只保存轻量目标、约束、已完成和下一步，不引入大型工作流系统。
- 编码任务最终回复标明结果、实际修改、验证证据和未完成项；未运行测试必须说明，不能把“建议运行”写成已通过。
- 先通过提示词与结果回灌改善行为。需要时增加一次有限续行：明确执行请求却没有相关仓库证据，或声称验证通过却无对应记录时，提醒一次继续或解释阻塞；不能对每个自然结束无限续跑。
- 无需修改、无法复现、环境缺依赖等允许作为有证据的结论；不能用“必须有 diff”逼迫制造改动。

验收：原始“帮我修复/实现”请求进入实作；“只解释/先规划”请求零写入；任务结束状态不以模型输出“完成了”单独决定。

### P2-R04 命令执行可用于真实开发（P0）

- 启动时确定并公开实际命令后端：Windows 优先可用的 pwsh，缺失时按明确配置回退 cmd；Unix 使用检测到且受支持的 Shell，提示词、工具描述与执行器三者一致。
- 不仅替换 shell 字符串：明确解释器参数、命令传输方式、UTF-8 解码与路径引用，验证 `.cmd` shim、空格和中文路径。
- 返回可机器判断的退出码、耗时、超时/取消标记、实际工作目录；stdout/stderr 流式展示并保留完整日志。
- 大输出写入受控结果文件，模型得到有边界的摘要与继续读取入口；默认不能因为“显示输出太多”杀掉正常测试。磁盘配额耗尽时明确停止与标记不完整。
- 超时/取消保留已收到日志，终止子进程树；stdin 关闭的命令若等待交互，明确提示非交互限制。
- 不默认支持永久 dev server 或后台守护进程；有界测试、构建、脚本执行先可靠。

验收：实际执行 pnpm/npm 测试、超过 120 秒但有持续输出的脚本、非零退出、超时和取消；退出状态准确，失败日志仍可查看，取消后不残留测试子进程。

### P2-R05 精准修改与变更证据（P0）

- 保留读后写、唯一匹配、文件版本校验、锁和原子写；不通过放宽校验来提高表面成功率。
- 匹配兼容 LF/CRLF 与 UTF-8 BOM，写回保留原文件格式；歧义仍失败，禁止默认模糊匹配猜测位置。
- 成功返回实际文件、变更区间和有界 diff；失败返回匹配失败、匹配多处、文件版本变化等可处理原因。
- 模型收到失败后重新读取最新片段再编辑；相同失败调用重复 3 次时停止该路径并调整方案或报告阻塞。
- 支持 Shell 产生修改的任务：交付核对真实工作区差异，不能只统计 EditFile/WriteFile 次数。记录任务开始已有改动，不能把用户原改动全算为 Agent 产物。

验收：中文、CRLF、BOM、重复片段、外部修改冲突均正确处理；成功记录与磁盘 diff 一致，失败无部分写入，不覆盖用户并发改动。

### P2-R06 修改 → 验证 → 修复闭环（P0，核心交付）

- 阅读 package.json/项目说明等确定已有检查入口；优先相关测试，再按变化范围运行类型检查或构建，不默认重建测试体系。
- 验证命令属于代码执行，复用现有授权；不在启动时自动执行未知仓库脚本，不把名称含 test 的命令当作只读。
- 验证失败将退出码、相关错误、日志位置送回同一任务，由模型定位、修改并再次验证，无须用户反复说“继续”。
- 默认最多 3 轮修复验证，受整体预算约束；记录每轮错误签名，避免同样命令、同样错误、无新改动地空转。
- 输出通过/失败/未执行/被阻塞四种验证结论。初始已失败的检查要记录并区分，本任务新增问题不能以“已有失败”掩盖。
- 低影响、仅文案变更允许合适的轻量验证；缺测试框架不强制安装依赖，说明限制并做可执行的替代检查。

验收：至少一个任务必须先出现真实测试失败，再自动修复并通过独立验收；造假“已通过”、删测试、修改断言掩盖问题均判失败。

### P2-R07 长任务预算、取消与失败恢复（P0）

- 拆开单次模型网络空闲超时、单个工具超时、整项任务预算；有工具进展不因原有两分钟全局计时被杀。
- 初始任务预算建议 15 分钟、最多 80 次模型迭代；命令默认 120 秒、允许明确请求延长至现有 600 秒上限；网络空闲超时建议 120 秒。均为待实现默认值，不是当前能力。
- 授权等待不计入有效执行时间，仍可取消；模型流、压缩摘要、工具和队列等待都响应同一取消信号。
- 429/可恢复服务端失败进行有界退避，初始最多 2 次重试，尊重 Retry-After 且受任务预算限制；401/参数错误不盲重试。
- 预算用尽给出已完成、现场、剩余步骤和继续入口；继续建立新预算并保留现场，不绕过预算无限循环。
- 命令是否已执行不确定时标记未知，先核对磁盘/进程状态；不自动重放可能有副作用的命令。

### P2-R08 完整工作现场持久化（P0）

- 保存结构化用户/assistant 消息、工具参数、结果和状态、任务摘要、验证记录及停止原因；稳定事件到来即落盘，不等最后回答。
- 工具开始先保存 intent、完成后保存 outcome，调用 ID 唯一。进程崩溃留下 intent 无 outcome 时标记未知，不能当未执行直接重放。
- 旧文本会话仍可读并明确恢复信息有限；新增版本字段，不破坏已有压缩边界、检查点和损坏尾部修复能力。
- 重启后继续当前任务前核对工作区和已变更文件；进程重启不意味着原命令仍在运行。
- 存储故障显式提示恢复不可保证，不能静默宣称已经保存；写入工具状态与消息保存不一致时标明证据缺口。

验收：修改文件后、验证完成前强制退出；重启能看到实际修改及待验证项，补验证后交付，不重复追加文件内容、不盲重放命令。

### P2-R09 大仓库定位和任务上下文（P1）

- Grep 增加上下文行、大小/结果上限、取消和 .gitignore 语义；优先可用 rg，提供受控降级，不能把“无权限/搜索失败”伪装成零匹配。
- ReadFile 返回已显示范围、总行数或继续位置，让模型知道文件未读完；大文件读写预算独立于界面预览。
- 保留现有项目指令加载；编辑子目录前补充该目录适用的 AGENTS/QICODE 约束，显式记录来源。
- 模型窗口/输出预算来自独立能力配置或已验证元数据，不按协议固定猜容量；缺失显示估计并允许覆盖。
- 压缩保留目标、用户约束、变更文件、验证结果、失败证据和下一步；已有结果溢出文件继续可访问，摘要失败不破坏原会话。

### P2-R10 服务执行的最小交互（P1）

- 展示当前动作、工具耗时、命令增量输出、等待授权及验证状态。中间文本进度应保留可见，不在下一工具调用时无痕消失；不展示隐藏推理。
- 权限弹窗可读完整命令、工作目录与实际规则范围。仅对用户明确批准的范围复用权限，不默认全放行。
- 支持运行中补充“当前任务”的输入；在本批已启动工具完成、下次模型请求之前消费。取消保留未消费补充。
- 通用后续任务队列、复制导出、复杂主题、团队面板扩建延后。保留原 Ctrl+T 团队入口，不以多 Agent 掩盖主 Agent 不能完成单任务。

## 5. 交付定义与成功门槛

状态必须区分：完成、改动但未验证、阻塞、失败、取消、预算耗尽。模型自然结束不等于交付成功；检查成功也不等于满足任意业务需求，因此真实基准仍由独立验收器判定。

本期必达：10 个固定任务各跑 3 次，共 30 次，新版端到端成功至少 24 次；每个任务至少成功 2 次。成功要求独立验证通过、满足范围约束且没有语义性人工提示续行。授权确认单独计数，不算语义提示，但记录打断频率。

假完成、错误副作用重放、覆盖用户并发修改、泄露凭据在确定性故障测试中必须为零；真实样本零观察不等于数学保证。报告原版结果和改善幅度，不预填尚未测量的收益。

不承诺超越所选模型的能力。若协议通过但语义任务普遍失败，先按同模型同预算对照分离运行时与模型因素；样本规模不足以直接声称与 pi 等效。

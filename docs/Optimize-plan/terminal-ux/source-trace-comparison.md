# QiCode 与 pi：源码调用链任务实测对比

日期：2026-11-07。比较目标是用户提供的同一句话：从终端 Enter 追踪模型请求、流式解析、工具执行、结果回传与回复展示，找出关键函数、调用关系和循环结束条件，依据 `src` 实现。

## 证据与边界

本次读取已有日志，没有重跑模型、没有调用收费 API。均为同项目工作区的这次源码分析任务；具体会话标识与原始记录保留在本地分析文件中。

pi 日志记录模型为 `deepseek-v4-flash`；QiCode 当时没有保存模型元数据，不能确认同模型、同端点和相同上下文容量。工作区不是固定提交，运行时间重叠。因此以下是这一轮用户体验观察，不是严格的产品性能排名。

桌面窗口采集初始化失败，当前聊天也没有附加终端会话。没有看到实时像素画面；展示评价依据双方最终 Markdown、工具日志和 QiCode 渲染实现。授权次数、授权等待时长、首个文本 token 延迟未记录，不估造这些指标。

## 解决思路与内容质量

### pi 值得采用的部分

先用主调用链建立全局图，再分别追踪 Enter、运行时、HTTP 请求、SSE、工具批次、结果协议转换、UI 和退出分支。这与用户要求的结构一致。

它实际展开了 `input-box.tsx`、`input-router.tsx`、`llm/client.ts` 的公共解析、两个 Provider、`conversation.ts`、`chat-view.tsx` 等环节，给出了从内部 `user/tool_result` 到 OpenAI `role: tool` 和 Anthropic `tool_result` 的转换。这是解释“工具结果怎么回到模型”的关键证据。

正常结束条件也说明得更准确：没有工具调用还不一定结束，需要继续检查 steering 和 `TaskDelivery.continuation()`。它把上下文恢复成功后的继续与恢复失败后的停止分开了。

不能照搬的是 664 行输出和大量 Bash 拼接。默认应提供可快速理解的主链和必要证据；详细展开应服务于用户需求。QiCode 应继续使用结构化读取与搜索工具，避免把适合 Git Bash 的命令照搬到 CMD。

pi 也并非完全准确。例如“每轮最多一次主模型请求 + 一批工具”不够严谨：一轮可因重试有多次请求尝试，多个工具会被拆成多个执行批次。其前面的批次说明更准确。不能因为答案更长、引用更多就不做核对。

### QiCode 的主要不足

`app.tsx` 读取 8 次、`agent.ts` 读取 7 次。其中部分分页合理，但也存在范围重叠：`agent.ts` 的 375 起始片段重复读取；`app.tsx` 的 965、1000、1020 等片段交叠。反复压缩与恢复让保留证据变得困难，是重复定位的合理解释，但不能凭日志把所有重读都归因于压缩。

它读到了主控制循环，却没有展开输入框的 Enter 分支、公共 SSE 解析函数、两协议结果转换和最终布局等关键实现。权限、重试等支线占了较多篇幅，结果回传的核心却只用“注入、进入下一轮”带过，未充分满足关键函数及调用关系要求。

核对后的具体错误：

| QiCode 原结论 | 实际实现 |
| --- | --- |
| `modelSwitchBusy` 时“直接丢弃” | App 的回调返回 `false`，InputBox 收到 `false` 后保留草稿，不清空输入 |
| `runSession` “把每个事件落盘” | 只在稳定事件、工具 intent/outcome、交付和停止等节点保存；流式每个 token 并不单独落盘 |
| 工具已经跑起来、结果未落地就标 `unknown` | `StreamingExecutor` 只有 `tool.execute` 已返回、随后结果保存回调失败时设置该状态；普通执行抛错不是同一分支 |
| 每条终止路径都有 delivery；除 interrupted 外都有 loop_complete | 某些早退分支没有 delivery；取消分支同样发 loop_complete，带 interrupted |

这说明 QiCode 本轮能给出概览，但还不足以作为精确调试参考。问题不只是措辞和排版，而是证据覆盖、上下文保留与分支核对。

## 展示与交互评价

1. 内容组织：pi 的“结论 → 主链图 → 关键环节 → 退出条件表”更适合这个任务；QiCode 的平铺段落更容易让读者丢失主线。
2. 阅读负担：pi 很完整但过长；QiCode 应吸收层次，不复制篇幅。复杂任务不能一律硬压成 3–5 个提升点。
3. 过程反馈：pi 更早出现工具动作。双方日志不足以评价实际首字时间、动画流畅度和鼠标体验。
4. 噪音：QiCode 原默认把每个完成工具的前 500 字直接插入聊天，多次读源码时会占据大量行。默认折叠结果、按需从任务详情查看，更符合持续阅读需求。
5. 输入与权限：本轮日志不能可靠还原每次用户确认，不据此声称任何一边“零人工干预”。此前已单独调整只读 Git 命令及授权快捷键。

## 本轮已实施的改进

### 优先修上下文，而非继续堆提示词

`Agent.recordReadFiles()` 原来在 ReadFile 成功后再次读整个文件，把工具没展示的内容也放进恢复状态。`RecoveryState` 又允许最近 5 个文件各 5000 tokens，最多约 25000 tokens，此外还有保留对话、技能等内容。

所以一次压缩后的消息估算仍可高达 30154 tokens，接近保守 32768 窗口。只加压缩冷却或换一段 prompt 无法消除这个负载。

现在：

- 只记录工具实际返回的页，不再次读全文。
- 文件和技能恢复预览缩短，整个恢复附件有总预算，默认上限约 4000 tokens，并随压缩目标缩放。
- 最近消息保留预算也随窗口调整，保持工具调用/结果配对。
- 不增加窗口假设，不为了躲压缩凭空宣称模型支持更大的上下文。

对旧会话 17 个压缩快照进行了离线负载替换测算：保留原摘要和原近期消息，仅替换恢复附件后，消息估算范围由最高 30154 降到最高 19168，最小 5997。没有重新调用摘要模型；不是完整 API 请求大小，不含 system/schema，也不能当作新速度或质量成绩。

### 吸收 pi 的追踪结构

源码追踪请求新增专门的只读提醒：先主链，后实际函数和关键数据转换，单独说明正常/异常结束条件。要求缺失环节明确未覆盖，不用常识或摘要补成事实；支线只讲与主链有关的部分，不强制套“功能提升”模板。

### 降低展示噪音与补足测量信息

新默认偏好折叠完成工具的结果，保留工具状态；已有显式偏好保留不覆盖，可在 `/settings` 调整。Logo 不变。

`run_start_v2` 新记录模型、协议与上下文/输出预算，方便后续对照；不保存凭据或端点。尚未新增完整请求首字、权限等待与费用追踪。

# 03-Loop 开发拆分

> 本文依据 `docs/plan/03-loop/spec.md`、`plan.md`、`task.md` 与 `check.md` 划分开发批次。
>
> 拆分只控制每次开发范围与学习节奏，不改变本章需求、架构边界和验收标准。当前只规划，不开发源码；开始每一次开发前，以当时源码为准校准旧接口名和文件名。

## 拆分原则

第 03 章不是“再添加几个工具”，而是把第 02 章的单轮工具闭环升级成能持续推进的 Agent Loop。它会同时改动模型事件、工具调度、对话历史、取消逻辑和 TUI，因此不能一次性塞进 `Agent.run()`。

拆分遵循四个原则：

1. 先建立循环需要的公共类型和数据边界，再写循环主体。
2. 先让 Agent 在没有 TUI 的测试中跑通，再把事件接到终端界面。
3. 每次只增加一条可观察的行为链路，并在同阶段补对应测试。
4. 逐步覆盖 `task.md` 的 T1-T8 和 `check.md` 的验收项，不提前实现后续章节的上下文压缩、权限确认或子 Agent。

主要依赖关系：

```text
事件与工具分类 + Conversation 历史
                ↓
Provider 流事件与取消信号
                ↓
Agent 多轮循环（先串行、能停止）
                ↓
工具分批并发、历史一致性、Plan Mode 占位
                ↓
TUI 消费事件、取消、轮次与 token 展示
                ↓
真实 API 跨协议验收 + 学习文档
```

建议拆成 6 次开发。每次结束后都停下，由你自己运行当前阶段能看见的效果、制造一个错误，再进入下一次。

## 第 1 次：Loop 的公共语言与历史基础

对应原任务：T1、T2、T3。

### 为什么单独拆

真正的循环还没开始前，各模块必须先能用同一种语言交流：Provider 需要告诉 Agent “文本来了、工具调用完成了、用量到了”；工具需要标明自己是只读、写入还是命令；Conversation 需要能保存每一轮的工具调用和结果。

这一步不请求真实模型、不执行循环。它只先建立合同，避免之后把厂商字段、工具分类和历史结构硬编码进大循环。

### 本次完成什么

- 扩展统一 `StreamEvent` 与 token 用量类型。
- 定义 `AgentEvent`：文本、思考、工具开始/结束、用量、轮次、结束、错误等。
- 为六个工具补充 `read`、`write`、`command` 分类。
- 让 `ToolRegistry` 能按当前协议导出工具定义。
- 扩展 Conversation：保存 assistant 的工具调用、工具结果和系统提醒。
- 为新类型、工具分类、历史顺序补单元测试。

### 阶段结果

可以用 fake 数据写入下面这段合法历史：

```text
user: "读取 A"
assistant: tool_use(ReadFile)
user: tool_result(文件内容)
```

此时仍不会自动进入下一轮模型请求。

## 第 2 次：Provider 流协议、用量与取消信号

对应原任务：T5。

### 为什么单独拆

Agent Loop 的每一轮都依赖 Provider。若先写循环、后补 Provider 的结束原因、用量和取消，循环只能靠猜测判断“这一轮是否结束”，出错时也无法干净停止。

这一阶段的目标是让 Anthropic 与 OpenAI 虽然使用不同 SSE 格式，但都输出统一的流事件；Agent 不应该看见厂商原始 JSON。

### 本次完成什么

- 统一 Provider 的流结束原因与 token 用量输出。
- 将 HTTP、鉴权、限流、网络等错误归一化。
- 确保 `AbortSignal` 能传到模型请求。
- 补 Anthropic 与 OpenAI 的模拟 SSE 测试：文本、工具参数分片、用量、结束原因、取消和错误。
- 回归第 01、02 章的纯文本与一次工具调用行为。

### 阶段结果

```text
Anthropic SSE ─┐
               ├─> 统一 StreamEvent -> Agent
OpenAI SSE ────┘
```

此时还没有多轮调度，但 Agent 已能可靠知道一轮流何时结束、消耗多少 token、是否被取消。

## 第 3 次：最小 ReAct Loop 与停止条件

对应原任务：T6 的循环主体、AC1-AC5、AC7、AC9 的核心部分。

### 为什么单独拆

这是第 03 章的核心跃迁：从“固定两次 Provider 请求”改为“只要模型还请求工具，就继续下一轮”。必须先用 fake Provider 和 fake Tool 跑通，避免真实 API 的不确定回复把循环逻辑搞复杂。

这一阶段先不追求并发批次、Plan Mode 和 TUI 效果，只解决：**何时继续、何时停止、历史怎样保持正确。**

### 本次完成什么

- 将 `Agent.run()` 改为可重复的请求模型 -> 收集响应 -> 执行工具 -> 回灌结果流程。
- 每轮写入 assistant tool use 和 tool result，下一轮带完整历史。
- 无工具调用时，把文本作为最终回答并结束。
- 支持最大迭代次数、Provider 流错误、用户取消、连续未知工具等停止条件。
- 工具输出在写入历史前截断，保护后续上下文。
- 用 fake Provider 证明“读 A 后再写 B，最后回答”的多轮场景。

### 阶段结果

```text
模型请求 ReadFile
  -> 工具结果回灌
模型请求 WriteFile
  -> 工具结果回灌
模型返回文本
  -> Loop 完成
```

这次完成后，离开 TUI 的 Agent 测试已经能证明真正的多轮能力。

## 第 4 次：保序分批执行与 Plan Mode 占位

对应原任务：T4、T6 的工具批调度与 Plan Mode、AC8、AC13。

### 为什么单独拆

“能循环”不等于“能安全地循环”。多个工具一起出现时，连续读取可以节省时间，但写文件和命令可能彼此影响，不能为了快而乱序。Plan Mode 同样会改变可用工具集合，属于 Agent 的执行策略，不应塞入具体 Tool 或 TUI。

将它们放在一起，是因为二者都在回答同一个问题：**当前这一轮，哪些工具可以执行、以什么顺序执行。**

### 本次完成什么

- 连续只读工具组成并发批次。
- 写入和命令工具单独串行，保持模型原始相对顺序。
- 即使并发工具先后完成不同，结果仍按调用原顺序回灌。
- 增加最小 `PermissionChecker` 占位：计划模式仅允许只读工具。
- 增加计划提醒文本，并实现“计划完成”后结束计划阶段的最小信号。
- 用带延迟的 fake Tool 测试并发窗口、串行顺序和结果保序。

### 阶段结果

```text
ReadFile + Grep  -> 并发
WriteFile        -> 等待读取批完成后执行
Bash             -> 等待 WriteFile 后执行
```

本次仍不是完整权限系统：不会弹窗确认，也没有路径沙箱。

> 当前实现状态：已完成。Plan Mode 同时在“发送给模型的工具列表”和“本地执行检查”两处限制非只读工具。

## 第 5 次：TUI 接入 Loop 事件与用户取消

对应原任务：T7、AC6、AC10-AC12。

### 为什么单独拆

前四次先证明 Agent 本身正确，才能把它接到 Ink。否则终端出现卡顿、重复渲染或取消失效时，无法区分是 Loop 编排问题还是界面状态问题。

本次只做“事件翻译成界面状态”，TUI 不决定是否循环，也不直接执行工具。

### 本次完成什么

- App 消费 `Agent.run()` 的异步事件流。
- 流式文本、工具运行/完成、错误和最终文本按真实顺序显示。
- 展示当前 iteration 与跨轮累计 token。
- 流式期间 Esc 或 Ctrl+C 取消本轮，不退出应用；空闲时 Ctrl+C 才退出。
- 取消后清理动态状态，仍能继续发起下一条对话。
- 用 fake Agent 或组件测试覆盖关键状态切换，并进行窄终端手工检查。

### 阶段结果

用户能直观看到：Agent 正在第几轮、调用了什么工具、工具何时结束；中途取消后回到可输入状态，而不是退出 QiCode。

> 当前实现状态：已完成 TUI 事件接入。自动化 TUI 测试与真实 Provider 手工验证统一留在第 6 次验收。

## 第 6 次：整章验收、真实联调与学习文档

对应原任务：T8、`check.md` 全部验收项。

### 为什么放在最后

完整 Loop 需要 Provider、工具调度、Conversation 和 TUI 同时正确。最后一次不再扩功能，只收集“是否真的可用”的证据，并根据最终代码写 Debug 和 Interview 文档。

验收分三层：

```text
单元测试：每个模块的规则正确
  ↓
fake 集成：多轮流程和异常边界正确
  ↓
真实 API + TUI：协议与用户体验真实可用
```

### 本次完成什么

- 类型检查、全量测试、构建。
- OpenAI/兼容端点多轮任务：读取 -> 写入 -> 最终回答。
- Anthropic（如有配置）执行等价场景，确认上层行为一致。
- 取消、未知工具、模型流错误、迭代上限、长工具输出和窄终端展示。
- 核对 `spec.md`、`task.md`、`check.md` 的每项证据。
- 基于最终源码生成 `docs/study/Debug/03-loop/README.md` 与 `docs/study-Interview/03-loop/README.md`，写入真实文件位置、函数名、行号、断点和故障实验。

### 阶段结果

- 能证明 QiCode 已从“单轮工具闭环”升级为“可控的多轮 Agent Loop”。
- 能明确说明尚未具备的安全能力：交互式权限确认、工作区沙箱、上下文压缩、持久化、子 Agent。
- Debug 和 Interview 文档只在这一阶段生成，绝不提前根据规划臆造。

> 自动化验收状态（2026-07-30）：`pnpm.cmd test` 通过 23 个测试文件、120 个测试；`pnpm.cmd build` 通过。真实 API + Ink 手工体验仍由用户在本机配置下完成；Debug 和 Interview 文档将在手工验收完成后，根据最终代码生成。

## 每次开发后的学习动作

每个阶段完成后，只做当前阶段的四件事：

```text
1. 亲自运行一个能看见的场景
2. 沿调用链回答模块四问
3. 制造一个本阶段故障并定位
4. 用自己的话复述：为什么这一部分需要单独拆
```

模块四问始终是：

1. 这个文件负责什么？
2. 谁调用它？
3. 它调用谁？
4. 为什么需要它？

第 03 章代码完全验收前，不生成 Debug 或 Interview 文档；开发前只阅读 Understanding 与本拆分文档。

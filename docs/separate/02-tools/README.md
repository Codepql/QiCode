# 02-Tools 开发拆分

> 本文依据 `docs/plan/02-tools/plan.md` 和 `docs/plan/02-tools/task.md` 划分开发批次。
>
> 拆分不会改变需求、架构或验收标准，只用于控制每次开发范围和学习节奏。当前只规划，不开发源码。

## 拆分原则

本章不是按文件数量平均切分，也不是把 T1～T19 逐项机械地各开发一次。拆分遵循四个原则：

1. 先稳定公共契约，再实现具体工具和协议适配。
2. 每次围绕一条可以解释、测试或观察的行为链路。
3. 工具实现与对应测试放在同一阶段，不把测试全部拖到最后。
4. 完整覆盖 `task.md` 的 T1～T19 和 `check.md`，不提前开发第 03 章的循环 Agent。

主要依赖关系是：

```text
Tool 契约 + Registry
        ↓
六个具体工具
        ↓
Conversation + Provider 契约扩展
        ↓
Anthropic / OpenAI 工具协议映射
        ↓
StreamingExecutor
        ↓
Agent 单轮闭环
        ↓
Prompt + TUI + App 装配
        ↓
跨协议端到端验收
```

建议拆成 8 次开发。每次结束后停止，由你亲自运行和体验当前阶段，再决定是否进入下一次。

## 开发前校准：先解决“单轮闭环”的冲突

### 为什么必须单独处理

`spec.md` 与 `task.md` 对工具结果回灌后的行为描述不一致：

```text
spec：结果回灌 → 再请求模型 → 生成最终回答
task T15：结果回灌 → 直接结束，不再请求模型
```

如果不先统一，最终会出现“工具确实读取了文件，但模型没有机会根据文件内容总结”的情况，AC8 也无法验收。

### 本次确认什么

正式开发前建议把边界确定为：

- 一次用户请求最多执行一批工具。
- 工具结果回灌后，允许再请求模型一次生成最终文本。
- 最终文本阶段若模型再次请求工具，只提示达到本章上限，不再执行。
- 第 03 章再实现可重复多轮的 Agent Loop、最大轮数和完整停止条件。

同时把规划中的旧文件名校准到第 01 章真实代码，例如 `Provider`、`conversation/types.ts`、`chat-view.tsx` 和 `system-prompt.ts`。校准只修正规划与真实基线的偏差，不改变本章需求。

### 阶段结果

- spec、plan、task、check 对“单轮”的定义一致。
- 后续开发不需要一边写代码一边猜闭环应该停在哪里。
- 本项属于开发前门槛，不计入下面 8 次代码开发。

## 第 1 次：Tool 契约、参数校验与注册中心

对应原任务：T1、T2、T3，以及 T11 中的 Registry 测试。

### 为什么单独拆

六个工具、执行器和 Agent 都依赖同一份 Tool 合同。先确定 Tool 接收什么、返回什么、怎样被找到，后续才不会让每个工具各自发明一套参数和错误格式。

本次建立的是工具系统的最小骨架：

```text
注册 Tool
  ↓
按名称找到 Tool
  ↓
取得模型可见的定义
  ↓
用统一 execute 入口调用
```

它不做任何真实文件或命令操作，因此出现问题时只需要检查类型、注册和 Schema，不会被文件系统行为干扰。

### 本次完成什么

- `Tool`、`ToolResult`、`ToolContext` 和工具分类。
- 字符串、整数、布尔参数的安全取值规则。
- 六个工具的模型可见 description。
- `ToolRegistry` 的注册、按名查找和列举。
- 协议无关的基础工具定义导出。
- 重名注册、未知工具和空注册中心的处理约定。
- Registry 与参数辅助函数测试。

### 阶段结果

- 可以注册一个 fake Tool，再按名称找到并执行。
- 未知工具不会导致空引用崩溃。
- 工具层不导入 React、Ink 或具体 Provider 类。
- 本次还不能读取文件、修改文件或运行命令。

## 第 2 次：只读工具链

对应原任务：T4、T8、T9，以及 T11 中 ReadFile、Glob、Grep 的测试。

### 为什么单独拆

`ReadFile`、`Glob` 和 `Grep` 都是只读能力，风险低于写文件和执行 Shell，并且能形成一条自然的代码探索流程：

```text
Glob 找文件名
  ↓
Grep 找内容位置
  ↓
ReadFile 读取准确上下文
```

把它们放在同一阶段，可以先理解“工具参数 → 工作目录 → 结果上限 → 结构化错误”的共性，又不会修改用户文件。

### 本次完成什么

- `ReadFile`：行号、offset、limit、文件不存在和目录错误。
- `Glob`：模式搜索、忽略目录、mtime 排序和数量上限。
- `Grep`：正则搜索、可选文件过滤、行号和结果截断。
- 工作目录和相对路径的统一解释规则。
- 不可读文件、非法正则、无匹配等结果语义。
- 三个只读工具的临时目录单元测试。

### 阶段结果

- 可以直接通过 Registry 调用三个只读工具。
- 能完成“找到文件 → 搜索关键字 → 读取上下文”。
- 大文件和大量命中不会无限进入输出。
- 此时模型还不会自动决定调用这些工具。

## 第 3 次：写入、编辑与命令执行

对应原任务：T5、T6、T7，以及 T11 中 WriteFile、EditFile、Bash 的测试。

### 为什么单独拆

这三个工具会改变本机状态或启动子进程，风险和调试重点明显不同于只读工具：

- WriteFile 可能覆盖文件。
- EditFile 必须保证替换目标明确。
- Bash 涉及退出码、超时、取消和子进程清理。

将它们集中在一个受控阶段，便于统一检查“成功结果、业务失败、异常和超时都不能让 QiCode 崩溃”。测试只能操作临时目录和无副作用命令。

### 本次完成什么

- `WriteFile`：创建父目录、创建或覆盖文件、返回写入摘要。
- `EditFile`：唯一匹配、0 次匹配、多次匹配和 `replace_all`。
- `Bash`：工作目录、stdout、stderr、退出码和超时。
- 子进程取消、输出上限和进程清理。
- `rg`、`grep`、`diff` 等“无匹配/有差异”退出码语义。
- 三个工具的结构化错误和单元测试。

### 阶段结果

- 在测试临时目录中可以完成写入和精确编辑。
- 命令失败、超时或输出过长时返回 `ToolResult`，不抛到顶层。
- 能解释为什么 EditFile 默认要求唯一匹配。
- 能解释为什么 Bash 的非零退出码不能全部等同于程序故障。

## 第 4 次：Conversation 与 Provider 工具契约

对应原任务：T10。

### 为什么单独拆

前 3 次解决“工具本身能不能工作”，本次解决“模型怎样提出调用、历史怎样保存调用”。这是工具层与 LLM 层之间的合同，Anthropic、OpenAI、Agent 和 TUI 都依赖它。

如果跳过这一步直接修改具体 Provider，厂商字段会渗入 Conversation 和 Agent，最终无法保持统一上层行为。

### 本次完成什么

- `ToolDefinition`、`ToolUseBlock` 和 `ToolResultBlock` 的统一结构。
- `ChatRequest` 增加可选工具定义，同时保持 `Provider.stream(request)` 单参数接口。
- `StreamEvent` 增加工具调用开始、参数增量和调用完成事件。
- Conversation 保存 assistant 的 tool use 和 user 的 tool result。
- 调用 ID 在请求、结果和历史之间保持关联。
- 旧的纯文本、thinking、多轮对话行为保持兼容。
- Conversation 和 Provider 类型测试。

### 阶段结果

- 可以用 fake 数据把一次工具调用及结果完整存进 Conversation。
- 纯聊天仍走原来的 Provider 接口。
- 上层类型中不出现 Anthropic `content_block` 或 OpenAI `delta.tool_calls`。

## 第 5 次：Anthropic 与 OpenAI 工具协议映射

对应原任务：T12、T13。

### 为什么这样拆

两个 Provider 解决的是同一个问题：

> 把统一工具定义和历史翻译成厂商格式，再把厂商的流式工具调用翻译回统一事件。

放在同一阶段可以直接比较协议差异，真正理解 Provider 抽象，而不是把两份代码当成两个互不相关的功能。

实现仍按顺序进行：

```text
Anthropic 请求与事件映射
  ↓ 测试通过
OpenAI 请求与事件映射
  ↓ 测试通过
相同 fake 场景做跨协议比较
```

### 本次完成什么

- Anthropic 工具定义注入。
- Anthropic `tool_use`、`input_json_delta` 和工具结果历史映射。
- OpenAI `tools[].function` 请求映射。
- OpenAI 按 tool call index 拼接 id、name 和 arguments。
- 两种协议的工具调用完成、usage 和 stop reason 映射。
- 多工具调用的独立参数缓冲。
- 非法或不完整 JSON 的明确错误策略。
- 两个 Provider 的模拟 SSE 测试及原有纯文本回归测试。

### 阶段结果

```text
Anthropic 工具流 ─┐
                  ├─→ 统一 StreamEvent
OpenAI 工具流 ────┘
```

- 不调用真实 API 也能验证工具参数拆包和粘包。
- Provider 能正确重建含 tool use / tool result 的历史。
- 本次只完成协议能力，还不自动执行工具。

## 第 6 次：StreamingExecutor 与 Agent 单轮闭环

对应原任务：T14、T15，以及 `tests/agent/agent.test.ts`。

### 为什么单独拆

这是本章最核心的编排阶段。之前的模块分别证明了“工具能执行”和“模型能请求工具”，本次才把它们连成用户可理解的完整行为。

需要把两个职责分开：

```text
Agent：决定当前流程走到哪一步
StreamingExecutor：把完整工具调用变成 ToolResult
```

如果 Agent 同时负责查 Registry、处理异常、计时和实现工具逻辑，它会迅速变成难以调试的大函数。

### 本次完成什么

- 协议无关的 `AgentEvent` 联合类型。
- `StreamingExecutor` 的提交、查找、执行、计时和异常兜底。
- 一次响应中的多个工具调用及结果收集。
- `Agent.run()` 的流式文本、thinking、usage 和工具事件编排。
- assistant tool use 与 tool result 写入 Conversation。
- 工具结果回灌后的一次最终文本请求。
- 最终文本阶段再次请求工具时达到本章上限，不继续执行。
- fake Provider + fake Tool 的 Agent 测试。

### 阶段结果

离开 TUI 也可以跑通：

```text
用户消息 → fake Provider 请求工具 → fake Tool 执行
→ 结果进入历史 → fake Provider 返回最终文本
```

- 工具失败不会中断 Agent 事件流。
- 能从测试中看清 Provider 调用次数、Conversation 消息顺序和工具调用 ID。
- 本次不实现任意次数循环；那是第 03 章。

## 第 7 次：系统提示词、工具展示与 App 接入

对应原任务：T16、T17、T18。

### 为什么单独拆

Agent 已经可以脱离界面运行后，再接 TUI，出现问题时才能判断是编排错误还是渲染错误。

本次只负责把已有 `AgentEvent` 翻译成用户看到的状态：

```text
AgentEvent
  ↓
App 状态
  ↓
ChatView / ToolDisplay
```

系统提示词也放在这里接入，因为工具真正对用户开放时，模型才需要知道选择工具和执行动作的规则。

### 本次完成什么

- 系统提示词增加 Agent 角色和六个工具的使用约定。
- 在 App 启动时创建并注册六个工具。
- App 从直接调用 Provider 改为消费 `Agent.run()`。
- 工具执行中、成功和失败三种显示状态。
- 工具名称、关键参数、耗时和截断后的结果摘要。
- 工具行进入 scrollback，顺序与文本回复一致。
- 流式文本、thinking 隐藏、token、双击 Ctrl+C 等第 01 章行为回归。
- 静态组件测试和 fake Agent 的 App 状态测试。

### 阶段结果

- 用户能在 TUI 中看到模型何时调用了哪个工具。
- 工具失败后输入仍恢复可用，可以继续下一轮。
- 窄终端不会因工具参数或长结果破坏布局。
- 原有纯聊天仍可使用。

## 第 8 次：真实跨协议联调与整章验收

对应原任务：T19，以及 `check.md` 的全部验收项。

### 为什么放在最后

真实联调依赖六个工具、两种协议、Agent 和 TUI 全部完成。本次不再增加核心功能，只收集证据，判断第 02 章是否真的达到 spec，而不是“代码看起来写完了”。

验收分为三层：

```text
自动测试：模块行为和边界稳定
  ↓
本地集成：完整链路不依赖外部偶然结果
  ↓
真实 API + TUI：用户体验和协议实际可用
```

### 本次完成什么

- 类型检查、全量测试和构建验证。
- Anthropic 与 OpenAI/兼容端点的相同工具任务。
- 读文件并总结的完整闭环。
- 写入、编辑、命令、Glob 和 Grep 的受控手工场景。
- 不存在文件、编辑不匹配、命令非零和超时的错误恢复。
- 大文件、长命令输出和大量搜索结果的截断。
- 多工具调用、scrollback 顺序和窄终端展示。
- API Key 不回显、程序退出后终端状态正常。
- 对 `spec.md`、`task.md` 和 `check.md` 逐项记录证据。
- 按最终代码生成 Debug 和 Interview 学习文档。

### 阶段结果

- T1～T19 全部有对应实现和验证证据。
- 两种协议在上层表现一致。
- 能明确说明当前没有权限确认、路径沙箱和完整 Agent Loop。
- 第 02 章满足完成标准后，才进入第 03 章。

## 每次开发的学习动作

每次代码完成后，不需要立刻阅读整章所有代码。只做当前阶段的四件事：

```text
1. 亲自运行本阶段可观察场景
2. 沿调用链回答模块四问
3. 制造一个本阶段故障并定位
4. 用自己的话复述为什么这样拆
```

模块四问始终是：

1. 这个文件负责什么？
2. 谁调用它？
3. 它调用谁？
4. 为什么需要它？

对应阶段代码完成后，再基于真实实现补充 `docs/study/Debug/02-tools/`；整章验收完成后，再生成 `docs/study-Interview/02-tools/`。文档中的函数名和行号必须来自最终代码，不能在规划阶段臆造。

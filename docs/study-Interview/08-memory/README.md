# 第八章 Interview：如何讲清 Agent 的持久化记忆

## 一句话项目描述

我为终端 Agent 设计了一条持久化上下文链路：会话用 JSONL 增量保存，恢复时从 compact boundary 重放；长期记忆由后台提取器异步生成并建立索引；文件修改在执行前备份，回滚时同时恢复文件和对话。

## 面试官可能追问

### 为什么 session 用 JSONL，不用一个大 JSON？

每条消息可以直接追加，崩溃时最多损失最后一条；读取时还能逐行跳过损坏记录。大 JSON 每次都要整体重写，文件越大风险和成本越高。

### 为什么恢复从最后一个 boundary 开始？

boundary 是已经压缩过的稳定上下文。只重放它之后的增量消息，可以减少 token，也避免把同一段历史重复注入模型。完整 `ConversationBlock[]` 仍保留，便于调试和精确恢复。

### memory index 解决什么问题？

索引只保存标题、类型、时间和路径。每轮先用索引筛选候选，再读取少量正文，避免把所有历史记忆塞进 system prompt。

### 为什么不能让模型直接选择文件路径？

模型输出是不可信输入。系统先把 selector 名称映射到已建立的索引，再读取受控目录中的文件；这样可以防止路径穿越和任意文件读取。

### 提取器为什么放在后台？

记忆提取不是当前回答的必要步骤。后台执行可以让用户先拿到答案；`inProgress/pending` 合并机制保证连续完成的轮次不会丢失，写入采用临时文件加原子替换。

### 为什么同一轮多次编辑只保存第一次备份？

用户期待 `/rewind` 回到这个 checkpoint 开始前的状态，而不是回到最后一次写入前。`pendingBackups` 按路径去重，snapshot 建立后清空，下一轮重新开始。

### 回滚为什么必须同时截断对话？

只恢复文件会产生“模型记得已经完成、磁盘却没有”的不一致。`FileHistory.rewind` 恢复磁盘，`Conversation.truncateTo` 删除对应消息之后的内容，两者必须作为一个逻辑操作。

### 某个目录不可写时为什么不能让 App 直接退出？

持久化是增强能力，不应阻断基础聊天。启动时捕获 FileHistory 或 memory 目录错误，保留对话能力，并让相关命令返回不可用状态，这是明确的降级策略。

## 可以主动补充的生产化思考

- 多进程同时写同一个 session 时需要文件锁或单写者队列。
- memory 需要去重、大小配额、敏感信息过滤和可审计删除。
- selector 结果要结合当前任务和权限上下文，不能因为“记忆里说过”就自动执行工具。
- snapshot 可以增加保留策略和磁盘配额，避免长期运行无限增长。
